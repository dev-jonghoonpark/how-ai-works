# 연합 학습을 이용한 LINE 스티커 추천

> [YouTube](https://www.youtube.com/watch?v=v-VwByrji0c) · Tech-Verse 채널 · 42분 · 발표: LINE 기쿠치(프로젝트 매니저), 대담: 야후 재팬 미야자키 다카시
>
> 한국어 더빙판의 자동 생성 자막을 바탕으로 정리했습니다. 자막이 흐린 수치는 "약"으로 적었습니다.

**한 줄 요약** — 후보 생성은 서버에서, 순위 재정렬은 단말에서 하고, 재정렬 모델은 **원본 로그를 서버로 보내지 않는 연합 학습(federated learning)** 으로 학습한다. 업로드하는 로컬 모델에는 **로컬 차등 프라이버시(LDP)** 노이즈를 더한다. A/B 테스트에서 스티커 패키지 다운로드가 **5.6%** 늘었다.

---

## 1. 서버·클라이언트가 머신러닝을 나눠 맡는 세 가지 방식

| 방식 | 학습 | 추론 | 장점 | 적합한 곳 |
| --- | --- | --- | --- | --- |
| 서버 중심 ML | 서버 | 서버 → 결과를 클라이언트로 전송 | 계산 자원·데이터가 많아 학습하기 쉽다 | 추천 |
| 온디바이스 추론 | 서버(글로벌 모델 배포) | 클라이언트 로컬 | 통신이 필요 없어 네트워크 지연이 없다 | UI 반응 |
| **연합 학습** | **클라이언트 로컬** → 서버는 통합(aggregation)만 | 클라이언트 | 원본 데이터를 서버로 보내지 않는다 | 프라이버시 보호 |

연합 학습 한 바퀴:

1. 무작위로 고른 일부 단말이 **자기 로컬 데이터**로 모델을 학습한다.
2. 학습된 **로컬 모델**(데이터가 아니라 모델)을 서버에 올린다.
3. 단말마다 조금씩 다른 데이터로 학습했으므로 서버가 **모델을 통합**한다(가중 평균).
4. 통합된 **글로벌 모델**을 학습에 참여하지 않은 단말까지 포함해 모두에게 배포한다.

## 2. 적용 대상 — 스티커 자동 추천

- 메시지 입력창에 글자를 치면(두 글자부터) 키보드 영역에 관련 스티커가 뜬다. 「ありがとう」, 「Thanks」처럼 표기가 달라도 같은 **의미 태그**로 이어져 같은 스티커가 나온다. 입력한 글자는 의미 태그를 고르는 데만 쓰인다.
- 태그는 크리에이터가 직접 달 수도 있지만, 지금은 **이미지를 분석해 머신러닝으로 태그를 예측**하는 것이 기본이다(일본어 태그만 약 500종).
- 대상 서비스는 **LINE 스티커 프리미엄**(구독형, 다운로드 없이 수많은 패키지 사용 가능). 그중 사용자가 직접 받은 스티커가 아니라 **시스템이 자동으로 내려받아 추천하는 스티커(auto download)** 의 배열을 바꿨다.

## 3. 모델 구조 — 세 방식을 모두 쓴다

### 1단계: 후보 생성 (서버)

- 입력: 서버에 쌓인 스티커 다운로드·구매 데이터 + 추정 성별·연령대 같은 사용자 특징(같은 세대가 자주 쓰는 스티커는 추천에 유효하다).
- 중간 산출물: **사용자 임베딩·아이템 임베딩**. 같은 공간에 놓이므로 벡터 유사도로 추천 목록을 만든다.
- 자동 추천은 "おはよう"용, "ようこそ"용처럼 **한 사용자에게 목록이 여러 개** 필요하다. 사용자마다 만들면 데이터가 너무 크므로 사용자 임베딩을 **클러스터링**하고, 클러스터별로 공통 후보 목록을 둔다.
- 결과: 약 100만 개 규모의 스티커에서 **약 100개의 후보**를 고른다. 학습·추론 모두 서버.

### 2단계: 재정렬 (클라이언트)

- 단말이 사용자·아이템 임베딩과 **재정렬 모델**을 내려받는다. 두 벡터를 넣어 후보마다 "이 사용자에게 얼마나 맞는가" 점수를 내고, 그 순서로 키보드에 배열한다.
- 학습 신호: 키보드에 **노출(impression)** 되었는가, **클릭**했는가.
- 추론: 글자를 입력할 때마다 단말에서 후보 수만큼 실행.
- 학습: 로그가 일정량 쌓이면, 부담이 크지 않도록 **단말이 유휴 상태일 때** 연합 학습으로 실행. 서버는 모델 통합만 한다.

| | 1단계 후보 생성 | 2단계 재정렬 |
| --- | --- | --- |
| 목적 | 약 100만 → 약 100개 | 100개의 순서 개인화 |
| 학습 데이터 | 다운로드·구매 | 노출·클릭 |
| 추론 | 서버 | 클라이언트 |
| 학습 | 서버 | 클라이언트(연합 학습) + 서버 통합 |

## 4. 플랫폼으로 만들기

다른 앱·서비스에서도 재사용하려고 스티커 전용이 아닌 **플랫폼**으로 개발했다. 요건은 둘이다.

1. 여러 앱이 붙어도 학습·추론이 잘 돌고, 공통 기능을 재사용할 수 있을 것.
2. 앱마다 프라이버시 요건을 각자 맞추기는 어려우므로 **프라이버시 보호를 플랫폼이 한곳에서** 맡을 것.

시스템은 (서비스 고유 / 연합 학습 공통) × (서버 / 클라이언트)의 네 칸으로 나뉜다. 앱은 서버 API를 부르듯 플랫폼에 **추론 요청**을 하고, 노출·클릭 로그는 서버에 로그를 흘려보내듯 플랫폼에 **던지기만** 한다. 데이터를 언제 어떻게 정리해 학습할지는 앱이 신경 쓰지 않는다.

플랫폼이 제공하는 기능:

- **A/B 테스트**
- **버전 관리** — 단말의 사용자·아이템 임베딩과 모델 버전이 정확히 맞아야 추론이 맞다.
- **학습 스케줄러** — 백그라운드 학습, 장래의 여러 모델 대비.
- **실행 환경** — iOS·Android 모두 지원하려고 **ONNX Runtime** 사용.

## 5. 프라이버시 — 로컬 차등 프라이버시

접근은 두 갈래다. ① 서버가 받는 데이터 양을 최대한 줄인다. ② **차등 프라이버시(differential privacy)** 를 적용할 수 있게 한다.

- 단말에서 로그 축적 → 로컬 모델로 변환(학습) → **노이즈 추가** 후 업로드. 단말에서 적용하므로 **로컬 DP(LDP)** 라 부른다.
- 차등 프라이버시는 "통계적으로 개인정보가 얼마나 지켜지는가"를 재는 기준이고, 그 기준을 만족시키려고 노이즈를 더한다. 노이즈 강도는 **프라이버시 파라미터 ε(엡실론)** 으로 조절한다. 노이즈가 섞인 모델은 다른 사용자의 모델과 구별되지 않으므로, 서버가 그 사용자가 어떤 스티커를 보내고 봤는지 추측하기 어렵다.
- 현재 구성: **가우시안 메커니즘**으로 노이즈, 서버 통합은 **단순 가중 평균**, 업로드할 때 **사용자 ID 제거**(통합에는 필요 없다).
- 남은 과제: ε을 적절히 정하기. 시스템이 복잡해 지금은 학습이 제대로 되는지 확인하는 단계라 **아주 작은 노이즈**로 설정해 두었다. 앞으로는 **셔플링(shuffling)** 도 도입해 보호를 강화할 계획.

## 6. 결과와 향후 과제

- A/B 테스트: 사용자가 **직접 내려받은 스티커 패키지 수 +5.6%**. 비교군과의 차이는 "표시되는 스티커가 연합 학습으로 정렬됐는가" 하나뿐이므로, 추천이 마음에 들어 받았다는 행동 자체의 상승으로 본다. 다만 충분하다고 보지는 않고 1·2단계 모두 개선 여지가 있다.
- 도쿄·후쿠오카·한국 세 거점, 일·한·영 세 언어, 엔지니어 30명 이상에 보안 리뷰·프라이버시 조사·홍보 조직까지 참여.
- 향후: 직접 구매한 스티커까지 재정렬 대상을 넓히고, 더 많은 사용자가 쓰는 서비스로 확대. LDP 파라미터를 제대로 정하고 셔플링을 도입해 프라이버시 기술을 실제 운용 가능한 상태로.

## 7. 대담(Q&A)에서 나온 것

- **왜 시작했나** — 2018–19년부터 보안 부서와 하고 싶던 일이었는데, 스티커 프리미엄 사업 부서가 추천 기능을 근본적으로 개선하고 싶어 해 맞아떨어졌다. "단순히 개인화만이 목적이라면 연합 학습이 아니어도 된다"는 점은 발표자도 인정.
- **어려웠던 점** — 기술적으로는 서버 데이터로 미리 시뮬레이션해 잘될 것이 확인된 방법만 골라서 큰 문제가 없었다. 어려운 건 개인정보가 걸린 복잡한 시스템의 가치를 늘어나는 관계자에게 설명하는 일.
- **기종 변경 시** — 단말 쪽 입력은 사용자 임베딩·아이템 임베딩·글로벌 모델 셋인데, 모델은 공통 배포되고 사용자 임베딩도 서버에서 만들므로 기기를 바꿔도 그대로 쓸 수 있다.
- **두 번째 기기(iPad·PC)** — 한 사용자가 여러 기기에서 학습하면 그 사람의 데이터가 과하게 반영될 수 있는데, 사용자 ID를 지우고 올리므로 서버에서 걸러낼 수 없다. 그래서 **보조 기기에서는 학습하지 않기로** 했다.
- **동기식인가** — 거의 **비동기**. 학습·업로드 시점은 LINE 앱이 아니라 iOS·Android의 유휴 스케줄링에 맡기고, 서버는 best effort로 일정 기간 모인 결과가 정해진 양을 넘으면 통합·배포한다.
- **모델 갱신 빈도** — 구체적 수치는 비공개, "비교적 높은 빈도".
